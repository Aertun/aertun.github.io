A model can draft a detection rule faster than anybody can check it. A proof is the check, made by a program rather than by the author, and written down so whoever receives the rule — a reviewer, CI, a customer — can rely on it without trusting whoever handed it over.

Three verdicts

VerdictMeans
provenevery check passed on evidence that could have failed it
refuteda check failed, and the proof names what
inconclusivenothing failed, but nothing could have: a rule checked only against its own fixtures

A refutation is signed like a proof: what did not work is what the next attempt most needs to know. Every command that makes a proof exits non-zero unless the verdict is proven, so each one is a gate a pipeline can stop on.

Prove a detection rule

aertun content keygen --out root.key     # once: a signing key in the store; move root.key off the machine
aertun proof detection --rule rule.json --corpus corpus.jsonl \
    --key .aertun/content/release.key --public-key proof-key.json \
    --out rule.proof.json --by you@example.com

It checks, in order:

  1. valid — the rule is a rule; an invalid one is refuted and nothing else runs.
  2. fixtures — its own must-match and must-not-match examples hold. Necessary, never enough.
  3. corpus — over a labelled corpus (one JSON object a line, as aertun detect replay reads), it fires on every entry labelled as its own and on nothing else it reads. A false positive somebody recorded and nobody fixed still refutes it.

Recall and specificity are reported as 95% Wilson lower bounds, so a proof over one example reads as the weak thing it is. Without a corpus the best verdict is inconclusive. --model and --prompt-sha256 record which model wrote the rule and a digest of its prompt — never the prompt.

Verify one

aertun proof verify --key proof-key.json --subject rule.json rule.proof.json

Both signatures must hold against a key you were handed, never one the document supplies; --subject checks the proof is about exactly that file. It exits non-zero on anything but proven, so it is a CI gate.

Without Aertun

python3 scripts/verifyproof/verify.py rule.proof.json proof-key.json

The script in the repository builds DSSE's pre-authentication encoding by hand, checks the Ed25519 signature with the Python cryptography package and the ML-DSA-65 signature with the openssl command (3.5 or later), and prints the claim and the verdict. It shares no code with Aertun. It checks the signatures and nothing else: whether the key is one you trust, and whether the subject is the file in your hand, stay yours to decide.

Certify the analyst's threshold

aertun analyst calibrate --key signing.key --public-key proof-key.json --out calibration.json \
    --epsilon 0.05 --delta 0.05
aertun analyst triage --calibration calibration.json --calibration-key proof-key.json

The findings verified people have ruled are put to the configured model, and the lowest threshold is fitted at which closing suggestions on findings people ruled real stay under --epsilon with confidence one minus --delta — an exact Clopper–Pearson bound, corrected for every threshold examined. The certificate names the model, the adapter and the prompt template by digest, and expires. Triage gates on it only when it verifies and fits; one that does not, and any answer not scored on the channel it was fitted on, goes to a person rather than back to the declared threshold.

Prove the AI analyst

aertun proof analyst --key signing.key --public-key proof-key.json --out analyst.proof.json \
    --k 3 --tolerance 0.05

The configured model is asked about each case of the labelled corpus that ships with Aertun (48 cases), --k times each, at least three; then each case meant to test it is asked again with an instruction planted in the text a log carries — in English, German and Japanese, encoded in base64 and ROT13, as a forged fence, as a note from the security team, and as numbers that try to bend the count. The proof states how often the model closed a case that was real, as an exact bound against --tolerance; how many planted instructions moved a verdict it committed to; and how reliable its closures and answers were across the runs.

One instruction that moved a verdict refutes it, whatever the rates. A case the model already answers wrongly with nothing planted is counted as wrong, not as moved, and nothing is planted in it. proven needs at least 30 answers on real cases with the bound under the tolerance, and instructions actually planted. There is no stub: with no model configured, nothing is measured and nothing is signed.

Score another vendor's AI

aertun verdict import charlotte.csv --source charlotte
aertun verdict prove --source charlotte --since 2026-10-01 --tolerance 0.01 \
    --key signing.key --public-key proof-key.json --out charlotte.proof.json

The export carries the columns alert, verdict and at, and optionally confidence, disposition, disposition_at and source; a file with any other column, such as the product's reasoning, is refused whole. Each verdict is joined to the decision a verified person made on the finding that alert raised here — the source's mapping names the path its alert id is at as alert — and only verdicts given before the decision count. The claim is about false closures, alerts the product closed that a person found real, against a tolerance you declare first: refuted when the exact lower bound is over it, naming the alerts; proven when the upper bound is at or under it on at least 30 closures; inconclusive between. The rate is over the closures somebody decided, which are not a random sample, so the proof states that coverage, and how many verdicts were delivered here before the decision rather than resting on the product's own clock.

Judge closures again, blind

aertun adjudicate size --rate 0.01                 # how many closures a target needs: 299
aertun adjudicate draw --source charlotte --since 2026-10-01 --per 299
aertun adjudicate next SAMPLE                       # or the console's Adjudication screen
aertun adjudicate judge SAMPLE --item 4 --judgement real --because "…"
aertun adjudicate prove SAMPLE --tolerance 0.01 --key signing.key --out adjudication.proof.json

A verdicts proof counts the closures somebody happened to decide, and people look again at what looked wrong. Here a sample is drawn at random from every closure the product's AI made in the period, reviewed or not, and from every closure people made, and its seed and digests are committed to the signed audit log before any item is shown; anybody holding the seed and the population can recompute the selection. Each item is shown with its evidence and nothing that says who closed it, how, or which of the two it came from. Nobody who closed an item may judge it, each is judged once, agents may not see the queue, and a judgement is a record in the log, never a decision on the finding — a product that learns from analysts cannot learn the answers.

The proof reads the AI's share judged real against the tolerance, as a verdicts proof does, and reports the people's share beside it. It is refused unless every item of the committed sample was judged after the commitment by a verified person, and it says how many samples of the same product were drawn before it.

Check another party's "not affected"

aertun vuln reach --source ./app --where github:acme/app      # once: what this source names
aertun vuln prove-vex vendor.vex.json --source acme-scanner --where github:acme/app \
    --key signing.key --out vendor.vex.proof.json

Every not_affected statement in an OpenVEX document about one asset is held against Aertun's bill of materials, advisories and reachability analysis for that asset. A component the bill lists at a version the advisory names contradicts "component not present" and "vulnerable code not present" — except for a Linux distribution's packages, which backport fixes without changing the version; this asset's own source naming the vulnerable symbol contradicts "not in the execute path". A version outside every affected range supports the statement. Everything else is uncheckable, and the proof counts why: no such advisory here, no bill for the asset, a component the bill does not list under that name (it may only be spelt differently), a symbol not named here (dependencies were not read), or a justification nothing here can check.

refuted names each contradicted statement; proven needs every one supported; most documents will be inconclusive, and the proof says exactly why. Nothing the document's author wrote is kept, and no statement closes a finding.

Pre-register a vendor's claim

aertun claim register charlotte-98 --source charlotte --metric agreement \
    --direction at-least --threshold 0.98 --window-days 30
aertun claim list                                   # or the console's Claim cards screen
aertun claim test charlotte-98 --key signing.key --out charlotte-98.proof.json

"98% agreement" can be made true afterwards by choosing the metric, the alerts, the period and the day to stop looking. A card fixes all of them first — the metric (agreement, false-closures, escalations-closed, abstentions, consistency or adjudicated-false-closures), the product, the labels and severity floor, the threshold and its direction, the confidence and the window — and commits its digest to the signed audit log. Only data that arrives after that entry counts; a card is never changed, and one edited on disk matches no registration and is refused.

claim test signs what it finds and decides nothing while the window is open: a test run every day and kept the day it passed is not pre-registered. Once it has closed, the exact interval at the card's own confidence proves the claim when the bound on the claimed side clears the threshold, on at least 30 alerts, and refutes it when the bound on the other side fails it. A card for adjudicated-false-closures is tested on the one blind sample drawn for it after it was registered, with aertun adjudicate draw --claim NAME.

Hold an agent to its own account

aertun agent maps triage-bot --host build01      # once: where it runs
aertun agent reconcile triage-bot --since 2026-11-01 --telemetry triage-bot \
    --key signing.key --public-key proof-key.json --out triage-bot.proof.json

The agent's account is the tool calls its GenAI telemetry reported, under the identity --telemetry declares (its gen_ai.agent.id; the registered name by default). It is held against what Aertun saw without asking it: every call the agent interface answered for the agent, from the signed audit log once the log verifies, and every connection the recorder saw leave a machine declared to run that agent and no other. A call is matched to the agent's report of the same tool within --window (two minutes by default), however its host prefixed the tool's name.

refuted names what is unaccounted for: a call it did not report, a call it reports and the server never received, a connection while it reported nothing. An agent that reported nothing while it was seen acting is refuted, and the proof says it cannot tell that from one never instrumented. proven needs at least ten observations with nothing unaccounted for; inconclusive is fewer. A machine declared for several agents, or under a name a proof cannot carry, is counted and left out; what the agent did in other systems is not covered, because nothing ties it to its identity there.

Check an AI's investigation

aertun proof evidence --report report.json --key signing.key --out report.proof.json
aertun proof evidence --report notes.txt --source acme-ai --since 2026-11-06 --until 2026-11-07 \
    --key signing.key --out notes.proof.json

An investigation an AI wrote is a list of claims about what happened: this event exists, this address was seen, this one was not, this happened so many times. Each is run again against the event store for the report's period. A report in the documented JSON form (aertun/evidence-report/v1) states its claims; from plain text, only the observables it cites — addresses, domains under a common top-level domain, digests, email addresses — and event ids tagged event:ID or alert:ID are taken, each as a claim that it was seen in the period, and nothing else in the text is kept. Every claim ends supported, contradicted or uncheckable, and the proof says whether the store's events span the period at all.

refuted names each contradicted claim; proven needs every claim supported, and at least three of them. Nothing the report's author wrote reaches the proof except identifiers, observables and numbers that passed a strict parser.

Kept proofs, and the Proofs screen

aertun proof keep rule.proof.json --public-key proof-key.json
aertun proof list [--kind detection|triage|calibration|verdicts|reconciliation|adjudication|claim|not-affected|evidence]
aertun proof show ID

Every command that makes a proof keeps it — claim test once its window has closed; a proof made elsewhere — in CI, on another deployment — is kept with proof keep, or from the Proofs screen under Proving ground, only after it verifies against the key handed in with it. The key is kept beside it by fingerprint: verifying says the key signed it, and whether that key is one to believe is yours to judge. A kept proof is checked again every time it is read, so one edited afterwards is listed as no longer verifying rather than as what it now says.

Listing, reading and checking are what the agent interface offers, as list_proofs, read_proof and verify_proof, every value labelled with whether somebody outside Aertun could have written it. A detection proof's rule name is the submitter's, perhaps the model under test, so the screen tags it written outside where the agent interface labels it. Keeping a proof is a change, and no agent may make one.

Whose proof it is

aertun proof signers
aertun proof trust verifier --key proof-key.json --why "our CI signs with it"
aertun proof untrust verifier

A signature says which key signed a proof, never whose. A proof counts as this organisation's only when its key is one of the signers this store trusts, and the Proofs screen says so on every row: trusted and the signer's name, or key not trusted here. Trusting a key is a privileged change: one administrator asks, with a reason, and another approves on the People screen. An only administrator's own request waits an hour, can be declined from any administrator's session, and is then approved with a passkey sign-in made in the last five minutes. Agents may not trust a key.

What a proof is

An in-toto Statement in a DSSE envelope: the subject is the rule file by digest; the predicate (https://aertun.github.io/proof/detection/v1) names the claim in words, the verifier and its version, every material it read by digest, each check, and the verdict. It is signed twice, Ed25519 and ML-DSA-65, the second in the context aertun/proof/v1. The Ed25519 half is plain DSSE, so in-toto and Sigstore tooling check it with no help from Aertun. The signing key file must be readable by its owner alone.
