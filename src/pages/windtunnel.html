The wind tunnel splices scripted malicious agent sessions into a recorded telemetry stream in a scratch store and measures whether the detections caught them. Nothing live is touched: the exfiltration step is a log line about exfiltration, written to a scratch spool.

aertun windtunnel list-scenarios
aertun windtunnel preflight
aertun windtunnel run --key .aertun/content/release.key --public-key scorecard-key.json --out scorecard.json
aertun windtunnel verify --key scorecard-key.json scorecard.json
aertun windtunnel diff old.json new.json       # the CI gate: fails on a regression

Scenarios

A scenario is data, never code: a malicious agent session as the security operations centre would see it, with a benign twin doing the legitimate version of the same work, on which nothing may fire. Six ship today: an injection through an issue, an MCP server's rug-pull, a read-then-exfiltrate chain, a slopsquatted install, a runaway cost loop, and a blind window in the recorder.

The scorecard

It names what ran before how it went — scenario digests, the stream's digest, the rule pack's version — then reports the miss rate first, with 95% Wilson bounds, and per family. Sealed with its own digest and signed with Ed25519 and ML-DSA-65, so a third party verifies it offline with the public key alone.

Whose rules

By default the scorecard is scored against Aertun's own reference rules, which were written beside the scenarios: it is a regression test of that pack, not an independent measurement. run --sigma DIR scores your own Sigma rules instead, joined at ATT&CK technique level, with the join's limits stated on the document.

Your estate's own weird-but-benign workflows

Benign twins are written beside the attacks and cannot know that your migration touches every table, that your agents make forty tool calls a second, or what your maintenance scripts look like. A benign session is one real workflow from your own event store that a person vouches for and a second administrator approves.

aertun benign capture nightly-backup --class backup --source aws/cloudtrail \
    --actor aws:svc-backup --since 2026-11-19T02:00:00Z --until 2026-11-19T03:00:00Z \
    --why "the 02:00 backup reads every object" --ticket CHG-1042 \
    --acknowledge aws.bulk-read
aertun pending approve ID                 # a second administrator
aertun benign list
aertun benign bundle --key signing.key --public-key bundle-key.json --out benign.json
aertun windtunnel run --sigma rules/ --baseline benign.json --baseline-key bundle-key.json --out card.json

A capture is refused when the selection holds an indicator the intelligence store knows, touches an entity a finding is still open about (unless you name the finding), or raises an alert you did not acknowledge by name. A baseline can block a rule that would catch what it holds, so it is held like an exception: two people, a reason and a ticket, an expiry (90 days by default, at most a year, and a capture older than a year is captured again rather than renewed), and aertun benign revoke, which needs nobody else.

Before anything leaves the store it is sanitised. Only the fields your rules read are kept. Names, addresses, domains and home directories become keyed pseudonyms that keep their shape: an address stays private or public and keeps the prefixes it shares with others, an email stays an email, a domain keeps its parents and a public provider's name. Credentials, card and bank numbers and telephone numbers inside free text become placeholders. Then your rules run on the raw and the sanitised events, and the capture is refused if any outcome differs, unless you keep that field as it is (--raw FIELD, recorded) or accept the loss (--accept-fidelity-loss, recorded). The pseudonym key never leaves the store, so the bundle — signed with Ed25519 and ML-DSA-65, every session named by the digest of its events — can go to a CI runner.

The run replays each live session into the base stream on its own, keeping its own gaps and arrival delays, and counts as a false positive every alert above ambient that a measurable rule raises on it: per session, per rule and per class, as k of n with 95% Wilson bounds. A rule that reads a field the bundle dropped, or compares a pseudonymised field with a value and was not in that session's fidelity check, is named as not measurable, and its fires on the sanitised events are not counted. Under --mutate the sessions are respelled too, so an allowlist written for one exact spelling shows. The rates describe the workflows you chose to vouch for, not a random sample, and the scorecard says so.

The gate, and accepted trade-offs

aertun windtunnel diff before.json after.json --accept accepted.json

Besides newly missed attacks and newly firing twins, the diff fails on every rule newly firing on a benign session, compared by the session's content digest. A rule change that catches an attack and fires on the backup job may be right, but it is a decision: an acceptance names that session and that rule, a reason, who accepted it and an expiry of at most 180 days, in a file reviewed with the rule change. An expired acceptance is ignored and named. If the rule was right and the session was never benign, revoke the session instead.

Messy pipelines

aertun windtunnel run --sigma rules/ --perturb all --baseline benign.json --baseline-key bundle-key.json

Detections are written against clean streams and run against messy ones. --perturb replays every attack and every benign session again under the faults real pipelines introduce: dup delivers a quarter of events twice; reorder adds arrival delay up to twice the stream's own 99th-percentile lateness; skew puts the busiest source's clock five minutes ahead; burst runs the session four times faster, each event keeping its own delay; drop-field removes the field your rules read most, as an upgrade renaming it would. Per fault, the scorecard reports the attacks missed, the catches that broke and the benign sessions that started firing. Every perturbation is deterministic from the seed, so two runs compare.
